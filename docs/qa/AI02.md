## Separate review passes

### Logic and contracts

Reviewed the public vision entry point, backend selection, LiteLLM adapter, and all three callers.
Prompts and generated Pydantic models still come from the existing vision tools.
The runner checks response version, UUID, connection type, expected keys, and strict field types.
A request with a schema requires a compiled consumer validator before inference.
Configured API Router fallback remains within the API adapter. A CLI selection cannot call that adapter.

### Edge cases

Reviewed missing configuration, unsupported capabilities, malformed images, unsupported versions, invalid output, timeout, and caller cancellation.
Tests reject file and HTTP image URLs, bad base64, oversized inputs, deep JSON, and non-finite values.
The deadline includes readiness and completion. A late adapter result is rejected.
Cancelled test adapters run their cleanup, and a subsequent request succeeds.

### Tests

The original 412-test suite passed before the change.
The final suite adds 42 cases, including both fake connection types and the actual public vision functions.
The tests distinguish mocked provider behavior from real model calls.
Published examples contain a small synthetic image and no private photo or credential.

The new contract is an internal boundary, not a published worker endpoint.
Existing multipart parsing and image pixel decoding happen before this boundary.
This change does not prove an end-to-end multipart, pixel, concurrency, or paid-token budget.
Existing LiteLLM logs and provider SDK buffering are not protected by the new wire envelope.
AI03 must check HTTP bodies, credentials, process groups, shared concurrency, temporary files, and cleanup at its own boundary.

### CPU and memory

Reviewed base64 size prediction, bounded JSON traversal, encoding, response parsing, and coroutine lifetimes.
Image limits are checked before the contract decodes any image. It decodes one bounded image at a time.
JSON traversal limits nesting and element count before encoding.
The API response byte limit precedes parsing and applies again to the repair response.
The SDK can already hold the full response. No transport-buffer or performance improvement is claimed.
The task adds no subprocess, disk output, background queue, or per-user cache.
